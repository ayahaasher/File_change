# 技术规格说明书：Web UI 日志重构与精细化操作

## 1. 背景与目标
当前 Web UI 在处理大规模文件时，Dashboard 的实时日志流过于冗长，影响用户对整体进度的把控。同时，用户对文件属性修改缺乏“按需选择”的灵活性。本次重构旨在：
- **降噪**：将过程日志移至后台，Dashboard 仅保留统计看板。
- **追溯**：在历史记录中提供沉浸式的批处理日志查看。
- **控权**：引入操作开关，支持独立控制重命名和三类时间戳。

---

## 2. 交互设计方案

### 2.1 Dashboard 实时监控 (Refactored Monitor)
- **视觉组件**：移除原有的控制台文本域。替换为三张 **统计卡片**：
    1. **已重命名 (Renamed)**：统计执行了 `re.sub` 且文件名发生变化的记录。
    2. **时间更新 (TS Updated)**：统计由于用户勾选了对应开关且执行了 `os.utime` 的记录。
    3. **总进度 (Total)**：当前处理位置 / 总匹配文件数。
- **实时性**：通过 SSE 接口推送 `{"renamed_cnt": N, "ts_cnt": M, "current": I, "total": T}` 数据包。

### 2.2 操作控制区 (Action Toggles)
- **参数矩阵**：
    - `modify_name`: 是否执行正则改名。
    - `modify_mtime`: 是否更新修改时间。
    - `modify_atime`: 是否更新访问时间。
    - `modify_ctime`: 是否更新创建时间。
- **逻辑绑定**：若未勾选对应项，后端在执行循环时将跳过该逻辑块，不对文件做对应修改。

### 2.3 历史详情弹窗 (Log Modal)
- **触发机制**：历史记录表格末尾增加 `📑 详情` 按钮。
- **弹窗样式**：玻璃拟态蒙层，支持独立滚动。
- **性能优化**：前端按需从 `historyData` 中取出对应任务的 `logs` 数组。

---

## 3. 后端数据结构变更

### 3.1 `history.json` 架构
```json
{
    "id": 1776071184,
    "time": "2026-04-13 17:34:00",
    "summary": { "renamed": 24, "ts_updated": 86, "total": 110 },
    "logs": [
        "2026-04-13 17:34:01 - file_01.txt 处理成功 (重命名 + 时间)",
        "..."
    ]
}
```

### 3.2 存储限制
- 全量记录最近 **100 条** 历史任务。
- 超出限制后，自动清理最老记录以维持性能。

---

## 4. 异常处理
- 若任务中途失败，应将失败日志标记为红色存入详情日志。
- 若用户未选择任何操作开关点击“开始”，前端应提示“请至少选择一项操作内容”。
